# ADR 0004: One OIDC role per deploy target

## Status

Accepted

## Context

An AWS account needs only one IAM OIDC provider for `token.actions.githubusercontent.com`. Behind it, a team can
create one shared "GitHub Actions" role with the union of every pipeline's permissions, or one role per pipeline
and target.

A shared role is simpler to set up, but its trust policy must list every repository and its permission policy must
cover every service. Any pipeline that can assume it can then deploy anything any other pipeline can.

## Decision

Each deploy target gets its own role. In this lab that is one role, `<name>-github-deploy`, which can:

- push to one ECR repository;
- register revisions of one task definition family, Fargate only and not privileged;
- update and describe one ECS service, without turning on ECS Exec, and only to a revision of that family;
- list and describe tasks in one cluster, to verify the rollout;
- pass only the execution role, only to ECS tasks.

Resource `*` appears only where the action has no resource-level permissions (`ecr:GetAuthorizationToken`,
`ecs:DescribeTaskDefinition`) or where a condition pins it to one cluster (`ecs:ListTasks`). The optional
read-only plan role ([ADR 0007](0007-read-only-plan-role.md)) is a second, separate role for the same reason.

## Consequences

- A new target (another service, a Lambda function, a bucket) means a new role with its own trust and permission
  policies. The README's Variants section shows what changes.
- The blast radius of a leaked session is one service.
- Role count grows with targets. That is acceptable at lab and team scale; at organization scale the same pattern
  is usually generated by a module.

## Compliance

Automated, in `infra/tests/iam.tftest.hcl`:

- No deploy action contains `*`.
- The statements that use Resource `*` are exactly `EcrLogin`, `EcsReadTaskDefinitions` and
  `EcsListTasksInOneCluster`, and the last one's `ecs:cluster` condition is the lab's cluster ARN.
- No statement uses `NotAction` or `NotResource`.
